# Git 提交规范

本规范适用于今后的提交，不改写既有历史。

## 标题

`type(scope): 中文摘要`；范围可省略。标题建议不超过 72 字符，说明主要意图，不以句号结尾。type 根据主要目的选择，scope 用本项目模块名并在下方登记。

| type | 用途 |
| --- | --- |
| feat | 新增功能 |
| fix | 修复错误 |
| perf | 性能优化 |
| refactor | 不改变对外行为的结构调整 |
| docs | 文档 |
| test | 测试 |
| build | 构建与依赖 |
| ci | 持续集成 |
| chore | 维护 |
| revert | 回退 |

## 正文与分类顺序

每个提交列出实际变化，按以下顺序归类：新增功能 → 问题修复 → 性能优化 → 结构重构 → 文档 → 测试 → 构建与依赖 → 持续集成 → 维护与回退。仅保留有内容的分类。相同类别的事项放在一起，每项说明一个具体变化。不要用文件清单代替行为说明。

正文末尾写真实验证结果及未验证项。破坏性变更用标题 `!` 和 `BREAKING CHANGE:` 说明旧行为、新行为与迁移方案。需要时添加 Issue、签名等项目要求的 trailers。

一个提交解决一个相关问题，实现与配套文档、测试可以同提交；无关变更拆开。不要提交敏感资料、构建缓存和原始私人过程日志。

相关变更记录与实现一同准备；小改动可用简短记录。总入口只维护导航，分类索引由 sync 重建，当前能力/验证状态集中维护在功能表。暂存后使用 check --staged 核对待提交内容，工作区检查不能代替提交快照检查。

每次提交前主动清理本任务遗留的临时日志、断点、探针、测试入口、临时 mock/硬编码返回和聚焦测试；保留正式日志、回归测试和夹具，不按关键词批量删除。清理后复跑相关验证，仅暂存本任务 hunks，再运行 check --staged；未处理的调试候选不能通过，确需保留的项按当前扫描 ID 逐项说明实际理由。记录清理、保留及验证结果，不把只读扫描当作自动清理或功能正确证明。

## scope 登记

| scope | 范围 |
| --- | --- |
| `host` | 宿主 SDK、账号归因、流解析、私有状态 RPC |
| `worker` | 维护回调、队列、调度、预算与状态格式 |
| `fingerprint` | 探针、评分、档位证据及参考数据 |
| `web` | 管理页和宿主桥接 |
| `release` | 打包、合同跟踪、验证矩阵、发布闸门 |
| `repo` / `docs` | 仓库治理与配置 / 文档与导航 |

新增 scope 先登记。可从项目根的[提交模板](../../.gitmessage)复制正文；首次接入只提供模板文件，没有配置 Git 自动加载，也没有安装 hook。

## 示例

以下仅为格式示例，不代表真实执行结果。

```text
fix(worker): 停用巡检时清除待跑复测

【问题修复】
- 计划停用后，标记待跑的巡检复测为已跳过，不重新调用模型。

【文档】
- 更新停用行为和本次变更记录。

【测试】
- 增加停用与复测竞争的模拟时钟用例。

验证：主机单元测试通过；未使用真实 OAuth 账号。
```
